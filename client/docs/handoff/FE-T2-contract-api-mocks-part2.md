# FE-T2: Contract copy, API client and mock API

Purpose: the frozen contract, one safe door to the API, and a browser-side mock server so every screen can be built before the real server exists.

## What was built
- `client/src/shared/index.ts`: input schemas (Section 7), response schemas, inferred types, `CONTRACT_VERSION = "1.0.0"`
- `client/src/lib/api.ts`: `apiFetch`, `apiFetchPage`, `ApiError`, `ADMIN_TOKEN_KEY`
- `client/src/lib/queryClient.ts`: shared TanStack Query client (no retry on 4xx, none on mutations)
- `client/src/mocks/`: `seed.ts`, `db.ts`, `slots.ts`, `whatsappMessage.ts`, `helpers.ts`, `errors.ts`, `browser.ts`, `handlers/{catalog,orders,bookings,index}.ts`, `mocks.test.ts`
- `client/public/mockServiceWorker.js` (generated by `npx msw init public/ --save`)
- `main.tsx` starts the mocks when `VITE_USE_MOCKS="true"`

## How other parts use it
- Fetch a list: `apiFetchPage("/products", productSchema, { query: { category: "wigs", page: 1 } })` returns `{ data, meta }`
- Fetch one thing: `apiFetch("/products/body-wave-bundle", productSchema)`
- Send data: `apiFetch("/orders", createOrderResponseSchema, { method: "POST", body: checkoutInput })`
- Uploads: pass a `FormData` as `body` (field name `file`)
- Errors: `catch (e) { if (e instanceof ApiError) e.code, e.status, e.message, e.details }`. `status 0` means offline, a bad response shape, or a missing `VITE_API_URL`
- Query keys: `["products", filters]`, `["product", slug]`, `["delivery-zones"]`, `["slots", params]`, `["services"]` (Section 9)
- Money: all values are kobo. Show with `naira()`
- After a successful order or booking: open the `whatsappUrl` the API returned. Never build the text in the page
- Mock rules: stock never below 0, unpaid holds expire (24h orders and bookings, 48h bridal), overlapping bookings give `409 SLOT_TAKEN`, home outside a zone gives `422 AREA_NOT_COVERED`, bridal needs its details
- Mock data resets on every page refresh. In tests use `resetDb(now)` and `getState()` from `mocks/db.ts`
- Seed IDs are stable: `seedId(group, n)` in `mocks/seed.ts`. Seed variant SKUs look like `VSS-8-3`

## How to test it
`npm run test`, then `npm run dev` and use the console checks in the part 2 file.

## Assumptions and known limitations
- `minPrice` and `maxPrice` are in kobo. `length` is in inches. Create order and create booking answer `201`
- `GET /products` includes variants. Tracking returns no phone or address, and a wrong phone gives the same 404 as a wrong number
- Public settings use `deposit: { bridalPercent }`. Hours, fees, deposit and policy text are sample values, marked `[REPLACE]` where the owner decides
- Mock bookings: slot `endAt` is the appointment end. Booking `endAt` includes the travel buffer after. The buffer **before** a home visit is blocked inside the mock only (see Open Question Q7)
- A bridal date is blocked in two places: slot generation (bridal services on a blocked date show no slots) and the booking's `eventDate`. Seed blocks one date 30 days from today
- `PATCH /bookings/manage/:token` is not mocked until CCR-1 is approved (FE-T10)
- Admin routes are mocked in FE-T11 to FE-T15. Mock admin login will be `admin@vsshair.test` / `Password123!`
- Mock photo upload returns a made-up Cloudinary link, so the image will not display
- Product `media` is empty, so screens show the sand placeholder until real photos are added (FE-T3)
- Rate limits and admin auth are not part of the public mocks
